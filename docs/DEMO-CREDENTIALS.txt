--------------------------------------------------------------------------------
 1. HOW TO OPEN THE PLATFORM
--------------------------------------------------------------------------------

 Console (browser)      https://localhost
 API base URL           https://localhost/api/v1
 API reference          https://localhost/api/v1/docs     (interactive OpenAPI)
 Health check           https://localhost/api/v1/health

 The development certificate is self-signed, so the browser warns once on first visit.
 Accept it and continue. Plain http://localhost redirects to https.

 Starting the stack:

     pnpm dev:up      first time: infra, migrations, RLS, contract deploy, seed
     pnpm dev         then: api + worker + web in watch mode
     pnpm dev:down    stop everything

  The chain is a local node for the demo. Avalanche C-Chain is the production target; the
  contract, its ABI and the client code are reused unchanged, so the migration is
  configuration plus key management. See docs/architecture.md section 10.4.

  To show that a licence is genuinely on-chain, open any published asset: the licence
  panel reports the token id, block number, gas used and transaction hash, all taken from
  the transaction receipt. The audit ledger shows the same transaction beside the
  application action that caused it.

 8. REST API ACCESS
--------------------------------------------------------------------------------

  Sign in with any account above, then use POST /api/v1/auth/token with an API key to
  obtain a bearer token for machine access.

  API keys are created and rotated in the console under Administration, or through the
  API. `pnpm seed` prints the label and the one-time plaintext of the key it creates for
  the Aurora workspace. The plaintext is shown once and never stored — only a hash and a
  visible prefix are kept.

  Quick check from a terminal:

      curl -sk -c /tmp/vs.txt -X POST https://localhost/api/v1/auth/login \
        -H 'content-type: application/json' \
        -d '{"email":"admin@aurora.dev","password":"VoidSpace!2026"}'

      curl -sk -b /tmp/vs.txt https://localhost/api/v1/auth/me
      curl -sk -b /tmp/vs.txt 'https://localhost/api/v1/assets?pageSize=5'


--------------------------------------------------------------------------------
 9. OPTIONAL SIGN-IN METHODS
--------------------------------------------------------------------------------

  Google SSO     Configured with GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET in .env.
                 Without those values the option is hidden; email and password always
                 work.

  Wallet (SIWE)  Configured with SIWE_ENABLED. A wallet connects, signs an EIP-4361
                 message, and links to the account. The seeded accounts have no wallets
                 attached, so this can be demonstrated from scratch.

  Invitations    An invitation link is generated by an administrator. No email provider
                 is configured, so the API returns the token once for out-of-band
                 delivery. This is a recorded open item, not a hidden shortcut.


--------------------------------------------------------------------------------
 10. RESETTING AND REPAIRING THE DEMO
--------------------------------------------------------------------------------

  Re-seed (idempotent, safe to re-run):

      pnpm seed

  The seed also repairs state that could not occur naturally. For example, an asset that
  holds an active licence is placed back in the published state rather than being left
  editable, because the API would refuse to publish it a second time.
